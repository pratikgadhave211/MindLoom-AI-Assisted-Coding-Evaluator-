# Agent API and IDE Bridge Implementation Plan

> **For implementers:** Use superpowers:executing-plans after the user asks to execute this plan. Implement in small steps and keep Python simple and commented.

**Goal:** Provide a local Python API that keeps one challenge workspace alive across multiple prompts, runs the existing agent in it, and streams progress to a future IDE.

**Architecture:** A local FastAPI service owns each attempt's existing Docker container and volume. The IDE-facing client sends a prompt for an attempt, receives a turn ID, and reads Server-Sent Events (SSE) for that turn. The IDE accesses files through this service so both the user and agent use the same container workspace; choosing and building the IDE adapter is a separate milestone.

**Tech stack:** Python, existing LangChain/LangGraph/LangSmith and Docker CLI, FastAPI, Uvicorn, pytest. Reuse `httpx` for API tests. Choose and pin FastAPI/Uvicorn versions compatible with the current Python and dependencies at implementation time, and record the tested versions.

**Spec and context:** This plan implements the user's requested IDE → Agent API → existing agent → shared Docker workspace flow. Existing agent implementation and `2026-11-08-edit-command-test-tools.md` define the current tool and isolation behavior. The user has not selected a final IDE.

## Current behavior to change

- `main.py` starts one workspace and stops its container after one prompt. `start_workspace()` creates an isolated attempt; its volume remains after `stop_workspace()`.
- `graph.py` makes a new message list for a prompt and `tracing.py` calls `graph.invoke()`, so progress is not currently streamed and later CLI runs do not continue the same conversation.
- File tools operate inside the container. A host folder with a similar name is not automatically the same workspace.
- Model calls are currently limited to five per prompt. Multiline edits can fail when model input uses LF and the file uses CRLF. Keep these visible as current limitations; do not pretend the API automatically fixes them.

## Global constraints

- Keep the code understandable to a beginner: ordinary functions, clear names, simple loops and conditionals, short comments on meaningful sections. Reuse the PostgreSQL checkpoint database; do not introduce an additional database or speculative abstractions.
- Keep API keys in the host controller. Do not mount `.env`, the host project, Docker socket, or hidden evaluation tests into the attempt container. Preserve the existing no-network, non-root, bounded-resource Docker setup; do not fall back to host command execution.
- First version is a **local single-user prototype**, bound to `127.0.0.1`. Require a randomly generated local bearer token for every endpoint and reject unauthorized requests; never expose the token, keys, raw internal state or Docker access to a model. CORS must not permit arbitrary websites.
- Conversation checkpoints and the thread-to-workspace-volume mapping are stored in PostgreSQL. Turn status and event buffers are in memory and are lost on service restart. Repo files and dependencies remain in Docker storage, not in PostgreSQL. Checkpoints can include prompts, model messages, and tool output.
- One active agent turn per attempt. Reject a second with `409`. Serialize file writes with agent activity: in this first phase the user can read while the agent runs, but writes return `409` until that turn ends.
- Stream actual events from the running graph; do not pretend events collected after `.invoke()` are live. Keep LangSmith tracing around the graph execution and retain each tool's actual name, call ID, status and order.
- Service shutdown explicitly stops known active attempt containers; it does not silently delete retained volumes. Container timeouts make the attempt unavailable and must be shown to the user. No production-grade multi-user isolation claim.

## Proposed API contract

All routes require `Authorization: Bearer <local token>`. Use JSON for requests and responses, except SSE. IDs are generated by the service; never accept container names, host paths, shell arguments, or image names from the client.

1. `POST /attempts` — create a fresh copy of the existing Flask challenge and start its container. Return `{attempt_id, status: "ready"}`; report Docker startup failure without claiming an attempt is ready.
2. `POST /attempts/{attempt_id}/turns` — accept `{prompt}`, run existing sanity checking, start one turn in the background, and return `{turn_id, status: "running"}`. Reject invalid prompts and simultaneous turns.
3. `GET /attempts/{attempt_id}/turns/{turn_id}/events` — stream SSE events with incremental event IDs: `turn_started`, `tool_started`, `tool_finished`, `answer`, `error`, and `turn_finished`. Include only the data needed by the client: tool name, call ID, status and bounded result, or final answer/error. A terminal event states `completed` or `failed`; an HTTP disconnect does not stop the turn.
4. `GET /attempts/{attempt_id}/files?path=.` — list a workspace directory using the existing container tool. `GET /attempts/{attempt_id}/file?path=...` returns file content plus a version hash. `PUT /attempts/{attempt_id}/file` accepts `{path, content, expected_version}` and rejects stale versions with `409`. No raw host paths; edits must be atomic and workspace-confined.
5. `DELETE /attempts/{attempt_id}` — end the attempt and stop its container. Reject while a turn is active in the first version. Retain its volume and return its volume name; do not delete user work automatically.

For authenticated streaming in a browser-based IDE, use `fetch` with an authorization header and read the SSE response stream; native `EventSource` does not allow a custom authorization header. The final IDE connection is deferred until the IDE is selected.

## Files

- Create `src/coding_agent/api.py`: FastAPI app, authorization, request validation, attempt/turn and file endpoints, SSE response. Keep HTTP details here.
- Create `src/coding_agent/attempts.py`: simple in-memory active attempt and turn records, start/stop, per-attempt lock, event buffers, background work and bounded retention. Reuse `memory.py` for persistent thread history and workspace mapping.
- Create or refactor `src/coding_agent/agent.py`: reusable turn execution used by the API and CLI, sharing existing model, Jev, graph, workspace and tracing setup.
- Modify `src/coding_agent/graph.py` and `tracing.py`: accept existing messages, append the next user prompt, reset per-turn counters, and expose actual progress events without losing trace context. Retain named tool steps and matching tool IDs.
- Modify `src/coding_agent/container_runner.py`, `workspace_core.py` and `container_workspace.py`: add a bounded, atomic, version-checked full-file save operation for the IDE's own edits. Use the same container workspace as existing agent tools. Rebuild the workspace image after runner changes.
- Modify `src/coding_agent/main.py`: call the shared turn function while preserving the existing one-prompt CLI behavior.
- Modify `pyproject.toml` and `README.md`; add `tests/test_api.py`, `tests/test_attempts.py`, and extend graph, CLI, tracing and Docker integration tests.

## Task 1 — Extract a reusable agent turn

**Interface:** `run_turn(prompt: str, attempt: Attempt, history: list, config: Config, on_event: Callable) -> dict` in `agent.py`. Returns the actual answer, tool outcomes, error, and updated message history; it does not start or stop the workspace.

- [ ] Test a fake model for a plain answer and a read → model → answer sequence. Assert the existing CLI uses the same implementation and does not expose API keys.
- [ ] Keep and extend the existing PostgreSQL two-turn tests: the second user message and previous complete tool-call/result pairs are sent to the model, in order; Jev and model/tool counters are per new user prompt. Do not automatically replay interrupted tool calls.
- [ ] Set a prototype conversation limit of 200,000 UTF-8 bytes of serialized message content. If exceeded, return a clear context-limit error without silently dropping tool-call/result pairs. Do not claim this is a token limit.
- [ ] Implement the smallest shared turn function and message handling. Preserve Jev as advisory and use the current 5-model / 10-tool per-turn limits. Confirm tracing wraps consumption of the graph stream, not merely construction of the generator.
- [ ] Run focused graph/CLI/tracing tests and then the offline suite. Test with tracing off and with a fake tracer; do not send real user code from tests.

## Task 2 — Own an attempt across turns

**Interfaces:** `create_attempt() -> AttemptRecord`, `start_turn(attempt_id: str, prompt: str) -> TurnRecord`, `close_attempt(attempt_id: str) -> None` in `attempts.py`.

- [ ] Test that two attempts get different Docker workspaces; two prompts on one attempt see its earlier edit; ending one leaves the other and the challenge template unchanged.
- [ ] Test missing/closed attempts, container start failure, simultaneous prompts, command timeout, shutdown and cleanup failure. On timeout mark that attempt unavailable and reject subsequent turns.
- [ ] Implement the in-memory active registry and lock, using the existing PostgreSQL thread-to-volume mapping and database advisory lock. Add an authenticated resume operation for a saved thread, or explicitly report that automatic API resumption is not yet implemented. Do not let model output choose an attempt or container. Retain volumes on normal close; provide explicit manual cleanup instructions.
- [ ] Use fake workspace functions for fast tests, plus a separately enabled Docker integration test for the two independent attempts.

## Task 3 — API and authenticated live events

**Interfaces:** `app` in `api.py`; start with `uvicorn coding_agent.api:app --host 127.0.0.1 --port 8000` and a locally generated token supplied through `AGENT_API_TOKEN`.

- [ ] Write API tests for missing/invalid token, attempt creation, accepted/rejected prompts, unknown IDs, already-running turn, Docker errors and close. Verify response bodies contain no API keys or host paths.
- [ ] Run the graph in a worker so blocking model/Docker calls do not freeze the API. Publish real `tool_started` and `tool_finished` events using graph/callback events; pass name and matching call ID. Bound each result and avoid dumping the full graph state or message history.
- [ ] Implement SSE with an incrementing event ID and an in-memory bounded buffer of the latest 200 events per turn. Keep a terminal status separately. Support reconnect via `Last-Event-ID`; if requested events were evicted, report an explicit replay gap rather than silently losing them. Remove completed turn event buffers when their attempt is closed.
- [ ] Test event order and actual streaming with a fake delayed tool: `tool_started` is received before the tool completes, `tool_finished` reflects the real result, and exactly one terminal event is emitted. Test reconnect, replay-gap, client disconnect, error and timeout. A disconnected observer does not cancel the agent.
- [ ] Check LangSmith still records graph and individually named tools when the worker streams the events. Test context propagation with a fake tracer and an optional harmless live trace when authorized.

## Task 4 — Shared editor file operations

**Interfaces:** `read_editor_file(attempt, path) -> {content, version}`; `write_editor_file(attempt, path, content, expected_version) -> {version}`. A version is the SHA-256 hash of the current file bytes; the container runner owns file I/O.

- [ ] Test list, read, successful save, stale-version conflict, missing file, invalid UTF-8, traversal, absolute paths, symlinks and payload limits. Preserve bytes on failure; use an atomic replacement. Limit client file content to 1 MiB and do not truncate a file on save.
- [ ] Add the operations to the existing container runner rather than reading from a Windows folder. For the local prototype, reject a client write while an agent turn is running; reject an agent turn while a client write is in progress.
- [ ] Docker integration: user saves a change through the API → agent reads the same change; agent edits a file → API reads the changed content and new version. Confirm two attempts and the template remain independent.
- [ ] These endpoints are a simple editor integration surface, not a full VS Code/Theia filesystem protocol. A future IDE adapter may instead attach to the same volume, but must solve concurrency and access control explicitly.

## Task 5 — Verification and handoff

- [ ] Run offline tests without real API keys and run opt-in Docker tests. Prove: create attempt → prompt → progress while running → file change visible → second prompt sees history and workspace → close → retained volume available. Assert test results reflect real tool exit codes.
- [ ] Document install/start commands, generating and using a local token, curl or PowerShell examples, SSE event fields, file saves, Docker setup, shutdown and manual volume cleanup. Show failures honestly when Docker or the model is unavailable.
- [ ] Verify the one-prompt CLI still works and LangSmith tracing can be enabled or disabled. Avoid printing raw graph state, secrets, or full file content unnecessarily.
- [ ] Report what is verified and what remains: actual IDE adapter, durable recovery, cancellation endpoint, production authentication, multi-user isolation, prompt quotas, evaluation, and stronger safeguards.

## Review focus

- Concurrent prompts or editor saves must not interleave unsafely; `409` is explicit and reproducible.
- SSE must not wait until the turn ends before emitting progress; disconnect/reconnect and bounded buffer overflow must be observable.
- Malformed model/tool calls, failed checks and rate limits must be sent as errors, not reported as successful fixes.
- Service restart loses in-memory event buffers and active registry; checkpointed histories and mapped volumes persist, but automatic API recovery is not implemented until explicitly tested.
- Sandbox limits and local token are prototype measures only; untrusted public multi-user deployment requires a separate security design.
